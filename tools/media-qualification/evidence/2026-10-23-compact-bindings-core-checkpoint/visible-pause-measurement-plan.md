# DP-24 first-pause visible-picture measurement plan

## What existing measurements prove

- `crates/deadpan-app/src/preview/harness/edit_latency.rs:52-96,145-181` runs the real reducer/service/renderer path and asserts an admitted, committed Hold plus a completed picture. It issues scripted egui events (`Driver::command`, `preview/harness.rs:1209`) and uses a small single-Original fixture. `--ui-check --mode performance` uses offscreen UI + picture GPU work, no screenshot readback (`ui_harness.rs:306`). It is useful for code-path regressions, not a native window or the 10k-Hold first-pause case.
- The harness starts input time in `Driver::events` (`preview/harness.rs:1160`), associates it with `command_admitted` / `command_committed` (`preview/harness/telemetry.rs:18-54`), then reports `input_to_commit_ms`. Its picture timer is ticket-bound; `PictureTelemetry::composed` is called after the harness's complete offscreen UI submission (`preview/harness.rs:946-969`, `telemetry.rs:235-265`). It is an end-to-end offscreen composition completion, not a physical display timestamp.
- `Presentation::presented` (`crates/deadpan-app/src/presentation.rs:567-579`) is the app's accepted-picture/background boundary: it is called after successful picture GPU submission, or for decoded background replacement. The native render call sites are `crates/deadpan-app/src/preview.rs:5337,5458`. This does not prove compositor/display scanout.
- `deadpan-render/src/gpu.rs:705-716` times shared-pipeline `queue.submit` to callback execution, which waits for the owner to poll. `docs/PERFORMANCE.md:213` explicitly excludes eframe's own frame submit/presentation and readback. These counters cannot stand in for the accepted picture or visible window.
- `perf edit` includes store commit + workspace refresh but no picture; see `docs/PERFORMANCE.md:126-136,193-198`. `doctor --project`/`perf scale` are also not a visible native edit measurement. Current spec target is Hold fallback visible under 100 ms (`docs/spec/DEADPAN_SPEC.md:1339`); DP-24 still calls for measured budgets (`1351`).

## Smallest truthful next measurement

Use an actual disposable 10,000-Hold project opened in the release native app, with its valid Original and the same first-pause cursor/selection setup as the slow case. Do not use `ui-check` for this target: its `--project` handling is for scripted project/fixture scenarios and it has no live desktop window (`ui_harness.rs:332-345`, `preview/harness.rs` scripted OpenProject flow). Keep the database and media private; hash/verify their identity before and after.

Add a narrowly gated, process-local monotonic trace for one `InsertTime` interaction, correlated by command/ticket/revision. Record distinct instants for: app receipt of the physical key/command input; command admission; durable commit result; refreshed workspace publication; picture request; decoded exact or Background reply; successful picture renderer submission; and `Presentation::presented` for the same ticket/revision (or accepted decoded background). Report one **input-receipt → accepted picture/background** elapsed value plus the separate input→commit and commit→refresh spans. Do not add nested durations to obtain the total. If an exact decoded picture is pending, the end event must match its request/ticket and committed revision; if a Background is accepted first, label it as such and retain the later exact-picture latency separately.

Drive the command in the visible native window with a real OS key event (or human keypress recorded by the app's input receipt hook); do not treat an AX action as a physical key unless its input delivery semantics are verified. Use Accessibility API polling without screenshots to verify the native window remains visible and the displayed-picture label/ticket/revision changes to the accepted result. AX is an independent state/visibility check, not a GPU or scanout timestamp. Keep the app foreground and record display refresh, resolution, power/thermal state and load. Capture the app/build/source identity, database hash, media identity, command, cursor, event trace and raw per-sample values. A single first-pause sample is diagnostic only; use at least 20 quiet committed samples for a DP-24 edit percentile claim, with each “first” sample made on a fresh equivalent package. Until that native run exists, report no target PASS.

## Falsification and limits

- Reject any sample with command rejection, ticket/revision mismatch, timeout, missing refreshed workspace, no accepted picture/background, stale AX label, or package mutation outside the intended history edit.
- Preserve the first accepted Background and report its tier explicitly; do not relabel it an exact Original picture. Confirm the exact picture eventually replaces it when the path promises refinement.
- Compare end-to-end trace with input→commit and commit→accepted spans, but never infer a hotspot solely by subtracting unrelated/nested timers. Repeat with trace disabled or low-overhead buffering to bound instrumentation effect.
- This measures app acceptance and native accessibility state, not photon-to-photon or physical scanout. The existing GPU callback includes poll delay; eframe submission/presentation remains uninstrumented. Those limitations remain in force even when AX confirms a displayed accessible label.
