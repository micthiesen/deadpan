# Point-target representation: source map and recommendation

Read-only. The §11.3 contract (docs/spec/DEADPAN_SPEC.md:666-672) explicitly says a Target has a normalized “region/point”, tracked transforms, confidence and manual overrides. No first-class point target type was found. Existing data is rectangle-only.

## Current rectangle model and semantics

- crates/deadpan-core/src/target.rs:115-145: TargetRegion { center: [u32;2], size: [u32;2] }; normalized millionths. Validation requires center ≤ 1,000,000 and each size in 1..=1,000,000. Zero-size points are rejected. center_ratio() gives exact framing coordinates.
- :164-180 define TargetSample and TargetCorrection, each embedding TargetRegion; :234-255 AttentionTarget embeds initial region plus samples/corrections/provenance/display aspect. Serde derives and strict unknown-field validation serialize this shape directly. :388-489 applies latest correction/sample and linearly interpolates center AND size only between consecutive Tracked/Interpolated samples; no interpolation across Lost, state change, correction or initial region. Lost therefore holds prior region.
- crates/deadpan-analysis/src/tracking/target.rs:46-65: target_region(NormalizedRect) quantizes a rectangle to millionths but forces both sides to at least one unit; rect_from_target(TargetRegion) reconstructs/clips a NormalizedRect. It cannot encode a point faithfully.
- Camera creation (crates/deadpan-app/src/preview/camera.rs:2315-2385) maps viewer center/corner back to source, chooses a broad quarter-visible rectangle with min 1% source side, and opens RegionDraft; camera_save_region (:2387-2457) saves initial region or correction using Operation::Save. Keyboard geometry is in crates/deadpan-app/src/navigation/camera.rs:53-115, 288-330: three fields (center/width/height), 1% source steps, minimum 1% side. The overlay (preview/camera.rs:2628-2639, 2726-2749) draws rectangles/handles only.
- TargetSource (core/src/target.rs:183+) is an enum for Initial/Manual/Tracked state, not geometry. TargetRegion has no kind or point variant. The codebase does use internally tagged Serde enums with serde(tag="type", rename_all="snake_case", deny_unknown_fields) (examples core/src/framing.rs:135+, core/src/marks.rs:39+), a suitable existing wire convention.

## Consumers that assume a nonzero rectangle

- Tracking worker boundary: crates/deadpan-app/src/project/service/targets.rs:368-407 selects the initial/correction region and requires rect_from_target before making a TrackRequest. crates/deadpan-cli/src/tracking.rs:1197-1204 exposes target_rect_at as a rectangle. Worker request types use NormalizedRect; Vision seed path (native/deadpan-track/src/main.rs:575+, native/deadpan-track/src/landmarks.rs:536+) accepts a rectangle and computes bounding-box/landmark behavior from width and height. A point cannot be passed safely as a fake zero-size rectangle. Point tracking needs its own tracking policy/worker seed semantics, or an explicit “point targets are not trackable yet” refusal.
- Corrections are geometry-specific: project/targets.rs:105-113 TrackMode::Correct and preview/camera.rs:617-639 corrections both carry TargetRegion; Camera correction starts from current region (camera.rs:2315-2333) and :2429+ retracks corrected tracked targets. With a geometry enum, correction must preserve/replace point-vs-region intentionally and tracking correction must reject point until supported.
- App overlay and inspector: preview/targets.rs:68-95,135-143,146-168 returns/evaluates regions, formats x/y/w/h, and names draw/tracking state. preview/camera.rs:2628-2639,2662-2701 makes rectangle overlays; picker fixed source points are already drawn separately as markers (:2703-2715). Reuse that point-marker convention for actual point targets; do not manufacture visible tiny rectangles.
- Follow/render path already only needs a center: crates/deadpan-plan/src/plan.rs:1763-1800 resolves region_at, takes region.center_ratio(), maps through display aspect, and composes inner layers. A geometry enum can give Follow a common center() accessor, preserving existing target clock/fallback behavior without inventing dimensions.
- Copying and serialization are structurally generic but schema-bearing: core/src/command.rs:740,904,954,1037,1913 stores/inverts/diffs full AttentionTarget values in command patches; store portable package copies preserve bytes/DB, and generation context serializes target records (crates/deadpan-cli/src/generation_context.rs:73). Add the point variant to typed target data and validators; no special-case copy/export algorithm appears necessary. Typed CLI tracking JSON (crates/deadpan-cli/src/tracking.rs:100,116,758-769) is a rectangle request API and should remain region-only or become a tagged geometry input with an honest unsupported-point response.
- Tracking/analysis conversion also assumes dimensions: crates/deadpan-analysis/src/tracking/target.rs:121-143 compaction compares center and size; :467-485 interpolates size with min 1. A point path needs point interpolation (center only), while rectangle samples keep existing center+size behavior.

## Recommendation

Use an explicit geometry enum, not size: [u32;2] with zero or a one-pixel/one-millionth “point” rectangle. Prefer a typed core shape like TargetGeometry::{Region(TargetRegion), Point { center: [u32;2] }} (rename existing rectangle TargetRegion to TargetRect if desired), used consistently for the target’s initial geometry, sample geometry and correction geometry. An alternative TargetRegion { shape: tagged enum } avoids rename but touches the same consumers. A single top-level geometry field with rectangle-only samples would make “point target” semantics unclear as soon as it is tracked or corrected; do not introduce that partial model.

Keep shared semantic access narrow: center_ratio() for Follow and source-to-canvas; render dispatch draws rect vs point cross/marker; track request conversion matches Region and returns a visible unsupported point-target error; point interpolation mixes center only and Lost holds center. If tracking points is intended now, it needs explicit point-specific Vision request/worker protocol and tests, not rectangle-width fabrication. Otherwise point creation/follow/correction can ship truthfully with tracking disabled for points.

Breaking source/SQLite/project and worker/CLI wire changes are authorized by the active goal’s AGENTS scope; no compatibility migration is needed. Still update all constructors/tests, JSON fixtures, command patch validation and portable-copy round trips together. Existing structs use strict Serde and compile-time field construction, so the compiler will expose most call sites; persisted JSON fixtures and subprocess protocol snapshots need deliberate search.

For keyboard creation, extend the existing Camera region editor with an explicit geometry-mode choice. Point mode exposes only center navigation (reuse RegionField::Center, same upright source coordinate and 1%-step/accelerated keyboard movement); Enter creates a TargetGeometry::Point at the exact center, Escape restores Camera draft. Keep rectangle mode and its width/height controls unchanged. Use the existing exact Original picture, Camera span and revision-bound Operation::Save path. The point is authored at the stopped picture, not inferred from a face tracker. Test source edges, center projection under rotation/aspect/crop, save/undo/redo, marker overlay, Follow resolution, point correction, and explicit refusal from T/:track.
