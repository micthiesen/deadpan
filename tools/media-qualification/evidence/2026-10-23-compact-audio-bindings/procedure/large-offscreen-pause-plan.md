## Evidence boundary

This is the smallest existing app/UI/service path that can measure the large structural workload and a ticket-matched accepted picture using the real Metal backend on this Mac. It is the repository's offscreen `ui-check` replay, not a physical window: keyboard delivery is scripted through egui, composition is offscreen, and callback completion is not display scanout. This matches the stated owner verification scope for replays on this Mac, but the report must say **offscreen acceptance**. Do not call it native-window visibility or claim photons-to-photons timing. Current diagnostics continue to omit eframe's own submission/presentation (`docs/PERFORMANCE.md:213`).

## Checks that make the trial invalid

- Package identity is the requested 10,000-Hold pristine fixture; no existing edit/history has altered its starting head.
- Cursor and command match the intended first-insertion boundary. Load/replay state is stable before the input origin is captured.
- Exactly one command is admitted and committed, with no rejection; committed revision differs from the starting revision.
- The new Hold and expected project duration are present after refresh; the picture completion is ticket/revision-correlated and its tier/outcome is recorded.
- Exactly one sample exists for each required timing metric. Timeout, stale picture, retained prior image masquerading as a new accepted Background, frame retry pathology, or machine load above the configured gate is INFO/failure, never PASS.
- Preserve all failures and reruns. The standard DP-24 percentile requires the project target's minimum sample count and quiet successful trials; a single run is diagnostic only. No threshold PASS follows from the plan itself.

## Correction: match the measured insertion exactly

The proposed `hold 11f` was the wrong duration for the retained `perf edit` first-pause case. `crates/deadpan-cli/examples/perf/edit.rs:21,338-372` uses `PAUSE_FRAMES = 12` and constructs `Command::InsertTime` at the target; use `hold 12f` in the UI replay.

`:hold 12f` is the insertion verb, even when the cursor is inside an existing Hold: `navigation/command.rs:1901-1909` parses it as `BeatEdit::InsertHold`; `preview.rs:1641-1656` routes that edit to `insert_pause`; `preview.rs:1761-1825` captures the current command context/cursor, checks pause eligibility, and applies a `SemanticInstruction::InsertPause`; `core/semantic/planner.rs:1186` plans that instruction as insertion. Changing an existing Hold's duration is the separate `hold-duration` command (`navigation/registry/entries.rs:892-900`). There is no requirement to select the containing Hold for `:hold`; the required state is an open project, Edit/Sequence view, ordinary non-scoped direct Sequence cursor, and a valid insertion boundary. Avoid Visual selection, Repeat/Retime nesting and a changed scope so the fixture exercises the ordinary InsertTime path.

At frame 17,933 in the 12-frame fixture, the cursor is inside Hold index 1,494 at offset 5 (zero-based); its preceding frame remains within that Background Hold. `deadpan-cli/src/pause.rs:68-127,169-175` resolves the new provider from that preceding `Picture::Background` to `HoldVideo::Background` + Silence, so this is a valid GPU Background path without inventing a Source. The new 12-frame pause splits/retains the old Hold's suffix. Set the cursor to 17,933 using the existing `ai_insertion::at` helper pattern (`preview/harness/ai_insertion.rs:477-487`) or the same deterministic navigation, verify it is the intended containing Hold and no visual/scoped selection is active, then invoke `hold 12f` once. Do not set the cursor at the start or use `hold-duration`, which would not reproduce the profiled insertion.
