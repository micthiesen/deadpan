# Reuse a successful Domain processing tape during policy

This checkpoint targets the second top-level physical Domain processing query inside Original policy preparation. The first query and every current-policy query remain real operations. General sound-bearing Split remains disabled until its full witnesses pass.

## Measured reason for the change

A scratch-only diagnostic build observed the actual one-selected-play Split failure at `prefix-two`, limited `0+4096`. Accepted canonical work conserved exactly against the unchanged global cap, cache work was zero, and the diagnostic table did not overflow. In the final diagnostic run, all 11,304 successful billed Domain policy calls reached the actual second top-level query. Their earlier processing queries and second queries each used 1,056,046 work units. This is gross duplicate work, not a measured net saving or a successful Split witness.

The probe also observed 2,543,720 already-billed query units before 5,458 successful prepared PCM-cache returns. Those query products also serve policy prediction. They are not free to skip, and this change does not retain them in the cache. All 3,407,314 observed transfer applications were nonidentity, so an identity shortcut was rejected.

Exact refusal prefixes varied near the cap. A controlled repeat of the same pinned phase-two executable and command changed collision comparisons in the existing address-hashed lookup by 26 units; 74 of 77 work rows stayed literal, and the remaining row differences reconciled the 22-unit accepted-work change. Raw prefixes and the initially rejected exact-prefix criterion are retained. This does not establish PCM nondeterminism, a latency improvement or a peak-memory improvement.

## Restriction and ownership

The existing processing walk co-produces a private terminal witness at its existing exhaustive content dispatch. Any exposed Stage or ProjectedStage makes the tape ineligible. There is no second eligibility traversal, new allocation or changed canonical weight. Successful Leaf/Bound-only queries never took the sole current `stop_at_preserve` branch; both walks stop at bindings. Preserve inside an opaque Bound or inherited retime is not globally forbidden. Recursive Bound policy keeps its ordinary independent queries.

Only the actual Domain factory creates the sealed product. It borrows the exact Domain, retains its original range and owns the successful processing query. The host bills that first query once. Finishing policy consumes the product, checks the same Domain address and range, and runs the existing current-policy inventory before reaching the old second-query phase. Eligible binding tapes are borrowed there. Exposed processing stages use the ordinary fallback, including its owned iteration and drop order. The completed pair yields the two ordinary owned queries without changing the host request or cache layouts.

Policy work and lookups report only operations actually performed while finishing policy. The already-paid first query is not rebilled or subtracted from fresh limits again. Root, incoming Retained and ordinary direct APIs remain separate paths. No caps, previous weights, refunds, cold/batch activation or PCM arithmetic change.
