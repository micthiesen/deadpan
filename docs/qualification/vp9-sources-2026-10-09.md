# SDR VP9 MP4 sources, 2026-10-09

DP-02 / DP-16, specification §16.3. This change adds SDR VP9 profile 0
eight-bit and profile 2 ten-bit 4:2:0 in MP4. It does not complete WebM/Opus,
VP9 HDR, AV1, ProRes, the remaining audio codecs or the source/operation
matrix. Implementation, review and verification are owned by the sole agent.

## Admission and decoding

The closed MP4 grammar accepts `vp09` with one bounded version-1 `vpcC`.
Profile/depth, chroma, level, flags and the empty initialization payload are
checked. An optional `colr` must agree. This follows the
[WebM project's MP4 binding](https://www.webmproject.org/vp9/mp4/).
The existing table, packet, metadata, geometry and shared opening budgets
apply before FFmpeg opens the descriptor. No library or runtime dependency
was added; pinned LGPL FFmpeg 8.0.3 already contains the software VP9 decoder.

Its MOV reader ignores the binding's chroma-subsampling field. The admitted
left/top-left siting now crosses the Rust/C boundary explicitly and configures
the decoder before the first picture. Ten-bit SDR retains the shared RGBA64
path, with no intermediate eight-bit quantization. Source receipts admit only
the observed VP9 layouts and progressive picture semantics; HDR remains refused.

Before the decoder's superframe splitter, a bounded parser checks every frame's
profile, explicit depth/range/matrix and fixed raster. The superframe index
must account for every payload byte and at most eight frames. An MP4 sample
contains exactly one displayed picture last, optionally after hidden references.
`show_existing_frame` presents its reference under the new sample PTS.
The pinned decoder ignores VP9 `render_size`, so a differing display size fails
explicitly instead of silently losing a transform. Changing raster, unsupported
profiles and malformed headers also fail before controlled decode.

Review of pinned `libavcodec/vp9.c::update_size` confirms that `ff_get_format`
runs before its dimension-dependent superblock and context allocations. The
existing immutable-limit callbacks remain in place. The earlier H.264/HEVC
fresh-export-GOP API continues to refuse other codecs; accepting VP9 sources
does not change export codec qualification.

## Fixtures and regression evidence

The [fixture manifest](../../native/deadpan-source/tests/fixtures/manifest.json)
pins seven small files. `generate_vp9_fixtures.py --check` reproduces all bytes
using development-only FFmpeg 9.0.1/libvpx 1.17.0, which is not linked into Deadpan.
Four lossless 96x64 clips have 12 pictures at 30000/1001, full/limited range at
both depths, independently authored color patches and motion, and retained
AAC ending at sample 19219. A two-pass 60-picture clip actually contains six
hidden altref pictures in superframes. Two more files contain a real one-byte
`show_existing_frame` after a key picture, at separate PTS 0 and 2002.

Native tests independently calculate BT.709 pixel values and chroma-edge phase,
check retained ten-bit low codes, compare 1/8/16-thread decode and repeated
backward seeks, and reject forged configuration, oversized/changing geometry,
render sizes and damaged superframe indexes. The existing container and
codec-configuration mutation campaigns now include these fixtures and `vpcC`.
An additional altref check compares each decoded picture directly with the
authored lower-half motion, including separation from adjacent source ordinals.

The previous packaged CLI from implementation `61cc5a96d2db9b42b56004af9581776700538b10`,
SHA-256 `fef1ee414655085387403f5087037b44c18625180036b795ecafeed54d8da4fd`,
refuses every final fixture as `unsupported_codec`. Fresh-home commands,
hashes and failures are retained in `/tmp/deadpan-vp9-before-20261009`.
The initial receipt-suite failure was an obsolete negative test classifying
VP9 itself as unsupported; it now tests the still-unqualified AV1 codec.
