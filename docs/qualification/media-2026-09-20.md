# Native media qualification, 2026-09-20

Gate A remains open. This isolated harness provides measured media evidence and
rejects two proposed dependency combinations. It does not qualify a finished
media adapter, GPU preview, audio output/DSP, inference, packaging, or release.

## Native library results

All successful files contain 120 video frames at 320×180 and AAC-LC stereo at
48 kHz. CFR is exactly `30000/1001`; VFR repeats durations of
`1001/30000`, `2002/30000`, and `3003/30000` seconds. The offset fixture starts
picture at `60060/30000` seconds, not zero. Video is encoded through
`avcodec_send_frame`/`avcodec_receive_packet`, muxed through libavformat, and
decoded/seeked through persistent library contexts.

These are single runs on tiny warm-cache fixtures while other development work
was active. They are not 1080p/4K performance results or stable latency claims.
The OS software timing varied substantially between runs. Hardware selection
was required with `allow_sw=0`; OS software selection used `require_sw=1`.
There is no implicit x264 fallback.

Every linear decoded picture also has its visible three-digit frame number read
from luma-cell centers and checked against the intended authored index, for 720
independent picture-identity checks across the six successful configurations.
A real encoded negative control swaps frame 10/11 pixels while retaining the
original timestamps. ffprobe verifies all 120 original PTS; the native probe
rejects it with `frame identity mismatch: decoded=11 expected=10 pts=10010`.
Self-consistent but incorrectly assigned picture hashes can no longer pass.

Each successful configuration passes 132 seek requests, covering every frame
plus repeated/nonmonotonic targets, with identical visible-plane hashes to its
own linear decode. All six successful files preserve exact rational PTS and
indexed presentation intervals. A retained decoded AVFrame remains unchanged
after decoding the rest of the file and flushing/reusing the decoder. The five
known YUV patch centers differ from their authored code values by at most the
asserted four-value tolerance. This is a CPU-plane test, not GPU/color-display
qualification.

All 36 checked channel/event pairs peak at the exact authored sample, with zero
sample offset after AAC round-trip. CFR's first/last events are samples `100`
and `191992`; the nonzero source's are absolute samples `96196` and `288088`.
AAC's encoder reports 1024 priming samples. The zero-start MP4 edit list removes
them; the offset fixture exposes those 1024 leading samples before authored
content and 320 terminal decoded padding samples after it. The harness compares
absolute PTS plus decoded sample index and validates the exact stream end, rather
than pretending every source starts at sample zero.

The native run exits **1** because a required candidate configuration fails;
the successful cases and negative control pass 246 Python assertions in aggregate plus the C
per-frame, packet, buffer, and seek assertions. The sanitizer run must be read
with the same scope: the known mux failure is still a failure, and sanitizing
the harness does not instrument every system/Homebrew library. The final
sanitizer run passes the same six configurations and 246 assertions with no
AddressSanitizer or UndefinedBehaviorSanitizer diagnostics; only the same
hardware B-frame mux failure remains. Both reports' harness hashes match the
checked-in C and Python sources.

## Failures that change the adapter decision

**Hardware B-frame timestamps.** The direct VideoToolbox encoder produces
`pts (1001) < dts (2002) in stream 0`; libavformat returns `Invalid argument
(-22)` while muxing. A separate stock CLI reproduction using
`testsrc2=size=320x180:rate=30000/1001:duration=4.004`, `h264_videotoolbox`,
`-bf 2 -g 15 -allow_sw 0` logs `Invalid DTS ... replacing by guess` and exits
zero. The native harness rejects the packet and does not repair timestamps by
guessing. FFmpeg's [pinned VideoToolbox encoder source](https://github.com/FFmpeg/FFmpeg/blob/n9.0.1/libavcodec/videotoolboxenc.c)
reduces H.264's requested B-frame count to a boolean and derives a DTS offset
from that. This is a relevant source-level lead, not a proven root cause.

For the next adapter experiment, use explicit hardware `max_b_frames=0`, or
explicit OS software `require_sw=1` when B-frame behavior is being examined.
Hardware produced a 16-frame GOP despite a requested 15; the report records it
and the around-half-rate check allows one frame. Software did not promise two
consecutive B-frames either: the displayed run produced a maximum run of one.
Keep the failing configuration as a regression case and qualify the shipping
FFmpeg/OS matrix before selecting final automatic export settings.

**VFR duration metadata.** Exact presentation timestamps survive, but 110 of
120 raw `AVFrame.duration` values do not equal the interval to the next
presentation timestamp. The stream duration underreports the authored video by
1001 ticks at `1/30000`, although final frame PTS plus its decoded duration and
the A/V container duration reach the expected end. `AV_CODEC_FLAG_FRAME_DURATION`
is enabled; merely setting durations does not fix this observation. Maintain a
PTS-based presentation index with explicit terminal-duration provenance. Do not
qualify VFR duration metadata or use stream duration alone as an edit boundary.

**rsmpeg/FFmpeg mismatch.** At
[`b21fcfde8bb1ffdc179504e370e330385baa9819`](https://github.com/larksuite/rsmpeg/tree/b21fcfde8bb1ffdc179504e370e330385baa9819),
rsmpeg is `0.18.0+ffmpeg.8.0`, MIT licensed, defaults to `ffmpeg8`, and depends
on `rusty_ffmpeg 0.16.7`. `cargo check --locked --lib --features link_system_ffmpeg`
against this host's FFmpeg 9 fails with five errors: four removed AVCodec
capability fields (`supported_framerates`, `pix_fmts`, `supported_samplerates`,
`sample_fmts`) and the `av_parser_init` codec-ID type mismatch. Do not add this
combination to the app. Qualify a separately pinned compatible FFmpeg build or
an updated binding behind the narrow adapter; no binding fork was started here.

## Cutlass extraction comparison

The inspected commit is
[`22437e2837340c7c57d62e438117f9a0fb4096d2`](https://github.com/1mrnewton/cutlass/tree/22437e2837340c7c57d62e438117f9a0fb4096d2),
version `0.7.0-alpha.0`, under MIT OR Apache-2.0. `cutlass-decoder` and
`cutlass-encoder` depend on the small `cutlass-core`, not UI/project-state
crates. On Apple, their native framework bindings are `objc2 0.6.4` and framework
crates `0.3.2`. The decoder also brings portable PNG/JPEG/GIF and Lottie/vector
dependencies, including `velato 0.10` and `vello_cpu 0.0.9`; its whole crate is
broader than Deadpan's immediate demux/seek boundary.

`cargo test -p cutlass-decoder -p cutlass-encoder --locked --no-default-features`
passes **96 tests**, with **one ignored manual benchmark**. Those include
native read/decode/seek, open-GOP recovery, retained GPU pixel-buffer existence,
native encode/decode round-trip, and a ten-second A/V export. Passing upstream
tests establishes only their assertions, not Deadpan's product contract.

Supplied upstream checkouts must match the pinned commit and have no tracked
modifications or untracked files. Ignored output, including `target/` and the
rsmpeg checkout's generated `Cargo.lock`, is listed in the report but excluded
from the committed-source tar snapshots actually built. Rsmpeg receives the
checked-in qualification lock in its isolated snapshot. Three regression tests
prove tracked/untracked dirt is rejected before build and ignored output cannot
enter the source snapshot.

A separate downstream Rust harness linked the unmodified crates and used the
same original fixtures. Five files each returned 120 exact linear PTS and
matched 12 subsequent seek hashes to their own CPU decode. The nonzero-start
fixture failed at frame zero: Cutlass returned a timestamp earlier than the
expected `60060/30000` seconds. This must be resolved before adoption. The
comparison is not cross-decoder byte equivalence and did not compare AAC PCM.

The [Apple decoder source](https://github.com/1mrnewton/cutlass/blob/22437e2837340c7c57d62e438117f9a0fb4096d2/crates/cutlass-decoder/src/apple.rs)
uses AVAssetReader, retains native buffers, cancels outgoing readers, and rebuilds
the reader for backward/long seeks. Its own source documents that coarse
keyframe scrubbing still pays the GOP-prefix decode cost. The decoder therefore
does not directly supply the specification's persistent demux/keyframe-index
architecture. The native lifetime patterns are useful references, but extraction
still requires contract adaptation, format coverage, and full failure tests.
The direct FFmpeg harness is narrower and preserves this offset fixture, but
requires the compatible-binding and shipping-build work identified above.

**Decision:** keep the spec's narrow direct FFmpeg/native media boundary. Do not
adopt all of Cutlass or either upstream dependency combination unmodified on the
strength of this run. Cutlass remains a source reference and measurable native
alternative; no extraction has passed the full Section 23.2 gate.

## License and remaining qualification boundary

The dynamically linked Homebrew FFmpeg library reports **GPL version 3 or later**,
with `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265` in its
recorded build. rsmpeg's MIT license does not change FFmpeg's configured license.
The [FFmpeg license documentation](https://ffmpeg.org/legal.html) describes how
enabled components affect licensing. This is a developer fixture build, not an
approved binary distribution, and no bundled GPL fallback is selected.

A source-level inventory of the actual shipping build and all transitive
components remains required. No app is packaged here. Also still open:
compatible Rust bindings; macOS 15 and other supported OS/hardware runs;
hardware decode and native/GPU ownership through completion; full color/HDR and
rotation interpretation; negative PTS, missing durations, anamorphic/interlaced
sources, 44.1 kHz/multichannel audio; HEVC/VP9/AV1/ProRes/MP3/Opus/image coverage;
long GOP, corruption and seek churn/memory pressure; audio output/DSP and audible
review; full-size/performance fixtures; preview/export equivalence; and actual
shipping encoder quality/bitstream, packaging, and clean-machine acceptance.
